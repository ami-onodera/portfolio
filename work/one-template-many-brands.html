One template, many brands

Three different refer-a-friend portals, a single template. The page structure stays the same for every brand, but each one brings its own assets, copy, logo and design identity. It’s how I build real portals: brand styling set in a Material UI theme and managed in a headless CMS.

The pain point

Every partner brand needs a portal that feels like its own

Styling, assets and tone of voice should all belong to the partner brand, so their customers never feel they have left the brand. At the same time, the platform has to ship every portal from one codebase and one content model. So the question becomes: how much can change, and where exactly should it change?

Brand fit

It has to feel native

Each partner needs its own styling, assets and tone of voice, in every portal.

Speed

It has to ship fast

Every portal comes from one codebase and one content model, on tight timelines.

Maintenance

It has to stay maintainable

A bespoke build per brand would be slow to deliver, hard to QA and impossible to maintain.

approach.log_▢x

The approach

I treat a brand as a set of design decisions, not a set of pages. Clients send very different amounts of material, so I boil each brand down to a few style elements: colours, fonts, weights and border radius. The layout, components and interactions are designed once, in Figma and CSS. Each brand only brings its own values, set in a Material UI theme in production. The shared template reads them and renders the portal, with no new markup and no new components.

What stays fixed, what changes

stays-fixed.txt_▢x
Designed once

Stays fixed

  • Page layout
  • Section designs: hero, how it works, products, rewards
  • Components: header, footer, steppers, product tiles and carousel, rewards table
  • Accessibility: headings, labels, focus states
  • Main interaction: CTAs open a referral widget, where users add their email and get their personal link, plus copy link
changes.txt_▢x
Per brand

Changes

  • Colours
  • Typefaces and weights
  • Border radius and CTA style
  • Copy and reward values
  • Order of page sections, interchangeable per brand
  • Logo
  • Assets
  • Custom sections are evaluated case by case

Details that make it feel native

client-assets.txt_▢x

Designed around client assets

Each brand provides its own images and logo, and I make them look good. I go through their website to understand their design, then apply it to our portal, so the UX feels seamless.

responsive.txt_▢x

Mobile first, fully responsive

Referral links are often opened on a phone, so I design mobile first and check every layout across breakpoints, from small phones to wide desktop screens.

custom-sections.txt_▢x

Customized sections

Custom sections and elements can be decided case by case, which makes each portal feel tailor made. Examples: banners, different ways to display products and extra CTAs.

What’s happening in the background

Every portal is held together by three layers. The template decides how a page looks, the CMS holds each brand’s values, copy and assets, and the content model decides how it all nests together. Change an entry and the page updates, with no new markup. Curious how that structure was designed? Take a look at the model.

problem-solved.txt_▢x

Problem solved

A pretty page is not scalable without a consistent template and content design supporting it. This is how you get a high quality outcome every time.
